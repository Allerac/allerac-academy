# 4.6 Backlog y prioridades

## Problema

Tu lista de ideas para la página tiene diez puntos: modo oscuro, corregir un enlace roto, foto nueva, sección de contacto, cambiar la fuente... Tienes una hora a la semana. ¿Por dónde empiezas? ¿Y si fuera un equipo de cinco personas con cien puntos?

*Intenta pensar en una respuesta antes de seguir.*

## Bloques

### 1. Backlog: todo lo que aún no se ha hecho
El backlog es la lista de tareas que esperan su turno. En GitHub, cada punto es una issue. El backlog no es una promesa de que todo se va a hacer: es la memoria del equipo, para que ninguna idea ni problema se pierda.

> **Notas para el tutor:** quita la culpa del backlog grande: todo proyecto tiene más ideas que tiempo. Cerrar una issue con "no lo vamos a hacer, por tal motivo" también es una decisión válida.

### 2. Prioridad: valor y esfuerzo
Para cada punto, pregúntate dos cosas:
- **Valor:** ¿cuánto ayuda esto a quien lo usa?
- **Esfuerzo:** ¿cuánto trabajo lleva?

Empieza por lo que tiene mucho valor y poco esfuerzo. Un enlace roto (todo el mundo tropieza con él, y la corrección es rápida) va antes que un modo oscuro (está bien, pero lleva más trabajo).

> **Notas para el tutor:** es la matriz de valor y esfuerzo (2x2). Excepción importante: un problema que impide usar el producto se salta la fila. No hacen falta números, "alto" y "bajo" bastan.

### 3. Las etiquetas ayudan a ver
Las etiquetas (*labels*) son marcadores de colores en las issues, como `bug`, `enhancement` (mejora) o `documentation`. Con ellas puedes filtrar la lista y ver, por ejemplo, solo los errores. Muchos proyectos abiertos usan la etiqueta `good first issue` para señalar tareas buenas para quien está llegando.

> **Notas para el tutor:** todo repositorio nuevo trae algunas etiquetas predeterminadas. Muestra que se puede filtrar por etiqueta en la lista de issues. `good first issue` es una muy buena forma de encontrar la primera contribución en un proyecto abierto.

### 4. Un tablero con columnas
GitHub Projects muestra las issues como tarjetas en un tablero con columnas: **Todo** (por hacer), **In Progress** (en curso) y **Done** (hecho). Arrastras la tarjeta a medida que la tarea avanza. Así todo el mundo ve, de un vistazo, qué se está haciendo y quién lo hace.

> **Notas para el tutor:** es un tablero kanban. Consejo de oro: pocas cosas en curso al mismo tiempo, idealmente una por persona. Terminar vale más que empezar.

### 5. Cómo se pone de acuerdo un equipo
En un equipo, alguien (muchas veces una persona de producto) ordena el backlog, y el equipo toma las tareas de arriba. Antes de empezar una tarea, te asignas a ella en la issue (**Assignees**) para que todos sepan que la tienes tú. Conversaciones cortas y frecuentes, a veces diarias, mantienen a todos alineados.

> **Notas para el tutor:** evita la jerga de metodologías (Scrum, sprints) a menos que el estudiante pregunte. Los nombres varían de un equipo a otro; lo importante es: una lista ordenada, una tarea a la vez, y avisar en qué se está trabajando.

## Misión

**Desde el sitio de GitHub (en cualquier dispositivo):**

1. Haz una lista de 4 a 6 ideas de mejora para tu `my-academy-journal`. La IA puede ayudar con ideas, pero elige las que tengan sentido para ti.
2. Crea una issue corta para cada una, con un título de resultado y un "Terminado cuando" de una o dos líneas. Ponle una etiqueta a cada una.
3. En la pestaña **Projects** del repositorio (o de tu perfil), crea un proyecto nuevo con la plantilla **Board** (tablero) y añade las issues.
4. Ordena la columna **Todo** pensando en valor y esfuerzo, y pasa la primera tarea a **In Progress**. Asígnate esa issue.
5. Envíale al tutor el enlace del proyecto (o una captura de pantalla, si el proyecto es privado) y explica por qué elegiste la primera tarea.

**Extra (opcional):** abre las [issues de allerac-academy](https://github.com/Allerac/allerac-academy/issues) y mira si alguna tiene la etiqueta `good first issue`. Si quieres tomar una, comenta en la issue antes de empezar y contribuye como en la lección 3.6: cuando editas un archivo de un proyecto al que no tienes acceso, GitHub crea un fork (una copia en tu cuenta) y el PR sale de ahí.

**Desde la tableta o el teléfono:** las issues, las etiquetas y el tablero funcionan en el navegador. En la tableta el tablero es cómodo. En el teléfono, la vista de tabla (**Table**) del proyecto suele ser más fácil de usar que el tablero.

**Cómo lo revisa el tutor:** hay de 4 a 6 issues con etiquetas, un proyecto con esas issues, la columna **Todo** ordenada, una tarea en **In Progress** asignada al estudiante, y una justificación de la elección usando valor y esfuerzo.
