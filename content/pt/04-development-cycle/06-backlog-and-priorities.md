# 4.6 Backlog e prioridades

## Problema

A sua lista de ideias para a página tem dez itens: modo escuro, corrigir um link quebrado, foto nova, seção de contato, trocar a fonte... Você tem uma hora por semana. Por onde começa? E se fosse um time de cinco pessoas com cem itens?

*Tente pensar numa resposta antes de seguir.*

## Blocos

### 1. Backlog: tudo que ainda não foi feito
O backlog é a lista de tarefas esperando a vez. No GitHub, cada item é uma issue. O backlog não é uma promessa de que tudo vai ser feito: é uma memória do time, para nenhuma ideia ou problema se perder.

> **Notas para o tutor:** tire a culpa do backlog grande: todo projeto tem mais ideias do que tempo. Fechar uma issue com "não vamos fazer, por tal motivo" também é uma decisão válida.

### 2. Prioridade: valor e esforço
Para cada item, pergunte duas coisas:
- **Valor:** quanto isso ajuda quem usa?
- **Esforço:** quanto trabalho dá?

Comece pelo que tem muito valor e pouco esforço. Um link quebrado (todo mundo esbarra nele, e a correção é rápida) vem antes de um modo escuro (legal, mas dá mais trabalho).

> **Notas para o tutor:** é a matriz de valor e esforço (2x2). Exceção importante: um problema que impede as pessoas de usar fura a fila. Não precisa de números, "alto" e "baixo" bastam.

### 3. Etiquetas ajudam a enxergar
Etiquetas (*labels*) são marcadores coloridos nas issues, como `bug`, `enhancement` (melhoria) ou `documentation`. Com elas, dá para filtrar a lista e ver, por exemplo, só os erros. Muitos projetos abertos usam a etiqueta `good first issue` para indicar tarefas boas para quem está chegando.

> **Notas para o tutor:** todo repositório novo já vem com algumas etiquetas padrão. Mostre que dá para filtrar por etiqueta na lista de issues. A `good first issue` é um ótimo jeito de achar a primeira contribuição num projeto aberto.

### 4. Um quadro com colunas
O GitHub Projects mostra as issues como cartões num quadro com colunas: **Todo** (a fazer), **In Progress** (em andamento) e **Done** (feito). Você arrasta o cartão conforme a tarefa avança. Assim todo mundo vê, de relance, o que está sendo feito e por quem.

> **Notas para o tutor:** é um quadro kanban. Dica de ouro: poucas coisas em andamento ao mesmo tempo, de preferência uma por pessoa. Terminar vale mais que começar.

### 5. Como um time combina
Num time, alguém (muitas vezes uma pessoa de produto) ordena o backlog, e o time puxa as tarefas do topo. Antes de começar uma tarefa, você se atribui a ela na issue (**Assignees**) para todo mundo saber que está com você. Conversas curtas e frequentes, às vezes diárias, mantêm todos alinhados.

> **Notas para o tutor:** evite jargão de metodologias (Scrum, sprints) a menos que o aluno pergunte. Os nomes variam de time para time; o importante é: lista ordenada, uma tarefa de cada vez, e avisar no que se está trabalhando.

## Missão

**Pelo site do GitHub (em qualquer dispositivo):**

1. Liste de 4 a 6 ideias de melhorias para o seu `my-academy-journal`. A IA pode ajudar com ideias, mas escolha as que fazem sentido para você.
2. Crie uma issue curta para cada uma, com título de resultado e um "Pronto quando" de uma ou duas linhas. Coloque uma etiqueta em cada.
3. Na aba **Projects** do repositório (ou do seu perfil), crie um projeto novo com o modelo **Board** (quadro) e adicione as issues.
4. Ordene a coluna **Todo** pensando em valor e esforço e passe a primeira tarefa para **In Progress**. Atribua essa issue a você.
5. Mande ao tutor o link do projeto (ou uma captura de tela, se o projeto for privado) e explique por que escolheu a primeira tarefa.

**Extra (opcional):** abra as [issues do allerac-academy](https://github.com/Allerac/allerac-academy/issues) e veja se alguma tem a etiqueta `good first issue`. Se quiser pegar uma, comente na issue antes de começar e contribua como na lição 3.6: quando você edita um arquivo de um projeto em que não tem acesso, o GitHub cria um fork (uma cópia na sua conta) e o PR sai de lá.

**Pelo tablet ou celular:** issues, etiquetas e o quadro funcionam no navegador. No tablet o quadro fica confortável. No celular, a visão em tabela (*Table*) do projeto costuma ser mais fácil de usar que o quadro.

**Como o tutor confere:** existem de 4 a 6 issues com etiquetas, um projeto com essas issues, a coluna **Todo** ordenada, uma tarefa em **In Progress** atribuída ao aluno, e uma justificativa da escolha usando valor e esforço.
